### 1.2 撮合引擎与链上系统联动架构

核心设计原则：**链上操作绝对不阻塞撮合引擎**，通过异步双轨并行 + 强哈希锚定保障性能与可信性。

```
用户下单请求
      │
      ▼
 SM2 签名验证
      │
      ├──────────────────────────────────────────┐
      │ 轨道 A（链下撮合，同步高优先级）              │ 轨道 B（链上存证，异步低优先级）
      ▼                                          ▼
 订单进入撮合队列                          订单哈希 + 用户签名
      │                                    → 存证网关缓冲队列
      ▼                                          │
 撮合引擎匹配                               毫秒级批量打包
      │                                          │
      ├──────────────────────────┐               ▼
      │                          │        上链: 订单存证合约
      ▼                          ▼               │
 成交结果                    生成撮合记录哈希        │ 链上确认回执
      │                          │               │
      ▼                          └───────────────┤
 清算系统执行清算                               锚定验证
      │
      ▼
 成交 + 清算结果哈希 → 异步上链 → 与原始订单哈希双向锚定
```

**链下-链上数据一致性保障机制**：
- 每个链下操作生成全局唯一操作 ID（UUID v7，含毫秒时间戳）
- 链上存证携带操作 ID，实现链下记录与链上存证精确映射
- 日终全量哈希校验，任何不一致自动触发监管告警

### 2.2 各角色详细操作边界与上链责任

#### 交易所运营方

**链上权限**：
- 身份合约：注册/撤销所有主体身份
- 订单存证合约：写入订单存证、撮合记录、成交确认
- 清算合约：触发清算存证、对账校验
- 合约升级：通过多签（≥3/5 核心节点）执行

**强制上链责任**：
```
事件                    上链时机        签名方          延迟要求
────────────────────────────────────────────────────────────
接单确认               接单后 50ms     交易所 SM2      <100ms
撮合记录               撮合完成后       交易所 SM2      <200ms
成交确认               清算完成后       交易所 SM2      <500ms
日终对账报告           23:59:59        交易所 SM2      T+0
链上链下差异告警        实时            交易所 SM2      立即
```

**越权禁止**：
- 禁止单方修改用户已签名的订单数据
- 禁止在未收到用户签名的情况下代理创建订单
- 禁止删除已上链的历史存证记录

#### 金融监管机构

**链上权限（只读 + 审计触发）**：
- 通过专属监管节点同步全量链上数据（准实时，延迟 <3s）
- 调用穿透查询合约：按订单 ID、用户哈希、时间范围、金额范围等多维检索
- 触发异常告警订阅：配置监控规则，超出阈值自动推送
- 上链监管指令：问询函、整改要求、处罚文书

**操作流程**：
1. 监管机构使用专属 CA 证书登录监管审计门户
2. 通过穿透查询合约实时获取链上数据，无需交易所授权
3. 发现异常时，在链上记录监管指令（含 SM2 签名确权）
4. 交易所收到链上监管指令后，在规定时限内上链执行结果

#### 投资者用户

**链上权限（个人数据相关）**：
- 提交带本人 SM2 签名的订单（签名由本地私钥生成，私钥不上链）
- 通过订单哈希自主核验本人订单的完整性
- 查询本人资产持仓链上记录
- 对争议交易提交链上异议申诉

**签名流程**：
```
用户在客户端构造订单参数
        │
        ▼
本地 SM2 私钥对订单摘要（SM3哈希）进行签名
        │
        ▼
签名 + 订单参数 → 发送至交易所 API
        │
        ├─── 交易所验签（用用户公钥验证签名合法性）
        └─── 验签通过后，交易所带自身签名一并上链存证
```

#### 资金存管机构

**链上操作边界**：
- 实时上链：用户充值/提现流水哈希（原文存在存管系统，链上仅存 SM3 摘要）
- 定时上链（每 5 分钟）：用户账户总余额哈希（与交易所上链数据交叉比对）
- 成交清算后：清算回执哈希（与对应成交单哈希一一绑定）

**双向对账机制**：
- 存管机构上链清算回执后，链上合约自动与交易所上链的成交记录进行哈希比对
- 比对一致：标记清算完成
- 比对不一致：自动触发告警，通知监管节点

## 五、订单全生命周期双轨并行时序设计

### 5.1 总体时序原则

**双轨并行**：链下撮合（高优先级，同步执行）与链上存证（低优先级，异步执行）完全解耦，互不阻塞。
**强哈希锚定**：每个阶段的链上存证必须锚定前一阶段的链上哈希，形成不可断裂的证据链。
**最终一致性保障**：允许链上存证有毫秒级延迟，但存证一旦完成即不可篡改，日终全量对账确保最终一致。

### 5.2 现货订单全生命周期时序

```
时间轴（T = 用户发起下单时刻）

T+0ms:    用户客户端构造订单，使用本地 SM2 私钥签名订单摘要
          生成唯一订单 ID，发送至交易所 API

T+5ms:    交易所 API 接收订单
          ├─ [轨道A] 验签通过后，订单进入撮合引擎队列（同步，立即返回接单确认）
          └─ [轨道B] 将订单哈希 + 用户签名 + 交易所接单签名 → 存证网关缓冲队列

T+6ms:    API 向用户返回接单确认（orderId + 接单时间戳）

T+5~50ms: [轨道A] 撮合引擎处理订单
          ├─ 限价单：加入订单簿，等待匹配
          └─ 市价单/可撮合限价单：立即执行撮合匹配

T+10ms:   [轨道B] 存证网关批量打包（每 10ms 或累计 100 条打包一次）
          → 调用 OrderEvidenceContract.batchEvidenceOrders()
          → 链上确认（FISCO BCOS PBFT，1-2 秒出块）

撮合完成时：
          ├─ [轨道A] 生成成交单，发送至清算系统（同步）
          └─ [轨道B] 撮合引擎输出撮合记录哈希 → 存证网关 → 上链

清算完成时：
          ├─ [轨道A] 持仓更新、资金变动（同步）
          └─ [轨道B] 清算系统输出清算哈希 → 存证网关 → 上链
               同时：存管机构收到清算通知 → 执行资金划付 → 上链清算回执
               → SettlementContract 自动比对，一致则完结，不一致则告警

日终 23:59:59：
          全量对账任务启动 → 生成当日全量哈希摘要 → 链上存证对账报告
```

### 5.3 拍卖订单时序（英式/荷式/密封）

#### 英式拍卖（升价竞拍）

```
T+0:      资产发行方（景区）调用 AssetRegistryContract 发起拍卖
          设置：起始价 + 加价幅度 + 截止时间 + 保留价哈希
          上链拍卖创建记录（交易所 + 景区双签）

T+n:      投资者提交出价
          ├─ 链下：实时更新最高价，向所有参与者推送行情
          └─ 链上：每次有效出价记录哈希上链（防止事后篡改出价记录）

截止时间： 确定最终成交方
          ├─ 链下：成交确认，通知双方
          └─ 链上：最终成交记录上链（含所有出价记录哈希锚定）
```

### 5.4 性能指标与保障

| 环节 | 链下延迟目标 | 链上存证延迟目标 | 保障机制 |
|-----|------------|---------------|---------|
| 接单确认 | <10ms | <100ms（异步） | 存证网关批量打包，FISCO BCOS 并行执行 |
| 撮合完成 | <1ms（市价） | <2s（异步） | 完全异步，不阻塞撮合 |
| 清算完成 | <500ms | <5s（异步） | 批量清算存证 |
| 日终对账 | — | <30min | 分批次全量处理 |

## 六、七大核心业务场景端到端融合流程

### 场景一：用户开户、身份核验与链上身份确权

```
步骤 1: 用户提交开户申请
   用户填写开户信息（姓名/证件/手机等）→ 提交至交易所 KYC 系统

步骤 2: 链下 KYC 核验
   交易所 KYC 系统 → 调用第三方权威机构（公安/银行/运营商）核验身份真实性
   核验通过 → 生成 KYC 档案（原文存储在交易所加密数据库）

步骤 3: 生成用户数字身份
   系统为用户生成/引导用户生成 SM2 密钥对
   用户私钥：用户本地保存（硬件钱包/加密存储），不传输至服务器
   用户公钥：提交至交易所

步骤 4: 链上身份确权
   上链数据（IdentityContract.registerMember）：
   ├─ KYC 核验结果（LEVEL + 时间戳，不含原始身份信息）
   ├─ SM3(证件号码)
   ├─ 用户 SM2 公钥
   ├─ 账户注册时间戳
   └─ 交易所注册确认签名

   事件：MemberRegistered(userAddress, kycLevel, timestamp)

步骤 5: 用户确认上链
   用户通过客户端查询本人链上身份记录，确认信息正确
   用户使用私钥签名确认 → 链上记录用户自确认时间戳

校验规则：
   - 后续所有操作需验证 userAddress 对应的 kycLevel ≥ 所需级别
   - 证件号哈希唯一性检查（防止同一证件重复注册）
```

### 场景二：用户充值、提现全流程链上存证与双向对账

```
【充值流程】

步骤 1: 用户发起充值申请
   用户在客户端发起充值（金额/方式）
   系统生成充值订单 ID（UUID v7）

步骤 2: 链下资金划转
   用户通过银行转账/支付机构 → 资金划至存管账户
   存管机构收到入账 → 系统记录入账流水

步骤 3: 链上存证（双方各自上链）
   存管机构上链：SM3(入账流水号 + 金额 + 用户标识 + 时间) → SettlementContract
   交易所上链：SM3(充值订单 ID + 到账金额 + 确认时间) → SettlementContract

   合约自动比对：
   ├─ 一致：标记充值确认，更新用户链上余额哈希，触发账户余额更新
   └─ 不一致：告警（差额 / 时序异常），通知监管节点，暂缓到账

步骤 4: 账户余额更新
   交易所系统更新用户可用余额（链下操作）
   同步更新链上用户余额哈希（SM3(最新余额)）

────────────────────────────────────────

【提现流程】

步骤 1: 用户发起提现申请
   用户使用 SM2 私钥对提现申请签名（金额 + 目标账户 + 时间戳 + nonce）
   防止重放攻击：nonce 链上验证唯一性

步骤 2: 风控审核
   链下风控引擎检查：余额充足 / AML 规则 / 提现频率 / 大额预警
   风控通过 → 进入提现队列

步骤 3: 存管机构执行划付
   交易所指令存管机构向用户绑定银行卡划付
   存管机构执行 → 生成划付流水

步骤 4: 链上双向存证
   存管机构：SM3(划付流水) 上链
   交易所：SM3(提现记录) 上链
   合约自动比对，一致后更新用户链上余额哈希
```

### 场景三：现货订单全生命周期链上融合

（详见第五章时序设计，补充特殊流程如下）

**撤单场景**：
```
用户主动撤单：
   用户签名撤单请求（含原始订单 ID + 撤单时间戳）→ 发送至交易所
   链下：撮合引擎从订单簿移除订单
   链上：OrderEvidenceContract.updateOrderStatus(CANCELLED, 用户签名)

系统/风控撤单：
   触发方生成撤单记录（含规则依据哈希）→ 签名 → 上链
   链上记录撤单主体（交易所/风控机构），防止无责任主体撤单
```

### 场景四：合约订单（期货/期权）全生命周期链上融合

```
下单阶段：同现货，额外上链保证金冻结哈希

持仓阶段：
   定时（每小时）上链持仓快照哈希
   强平线监控：风控系统实时监控，触发强平条件时：
   ├─ 链下：立即执行强平撮合
   └─ 链上：RiskControlContract.executeRiskAction(FORCED_LIQUIDATION)
           上链：强平原因（触发强平线的价格快照哈希）+ 强平执行记录

交割阶段（到期交割）：
   系统自动生成交割记录
   链上：上链交割价格（来源：价格预言机哈希） + 盈亏结算哈希
   存管机构：上链资金交割回执

到期归档：
   合约到期后，全量链上数据自动生成归档哈希，迁移至链下合规存储
```

### 场景五：订单撤单、异常处置、风控干预全流程链上留痕

```
异常检测 → 处置 → 留痕 完整链路：

[检测阶段]
   风控引擎持续监控：大额异常订单 / 高频洗单 / 价格操纵特征 / 对敲交易
   检测到异常 → 生成异常记录（anomalyId）→ RiskControlContract.recordAnomaly()
   上链：SM3(异常详情) + 风险等级 + 相关订单哈希

[审批阶段]（重大处置需双签）
   风控机构负责人 + 合规审查员 → 2/3 多签确认处置方案
   上链：SM3(处置方案) + 多签记录

[执行阶段]
   RiskControlContract.executeRiskAction() 上链处置指令
   交易所执行：限制下单 / 强制撤单 / 冻结账户
   链上同步记录执行结果，与处置指令哈希锚定

[申诉阶段]（用户异议）
   用户通过客户端提交申诉（含证据材料哈希）→ 上链存证
   交易所/风控审查申诉 → 审查结论上链
   监管机构可随时查看完整处置 + 申诉记录
```

### 场景六：监管机构穿透式审计、订单批量核验、异常核查

```
[日常穿透查询]
   监管人员登录专属审计门户（CA 证书认证）
   选择查询维度：
   ├─ 按用户哈希查询：所有关联订单 → 成交 → 资金变动
   ├─ 按时间范围批量导出：生成 Merkle 证明，可离线验真
   ├─ 按金额异常：超阈值订单列表，含完整证据链
   └─ 按订单 ID 精确追溯：从下单到清算的全链路一键展示

[批量核验]
   上传订单 ID 列表 → 调用 ComplianceAuditContract.batchVerifyOrders()

   差异项自动标红，生成核验报告（含核验时间戳，链上存证）

[异常专项核查]
   监管机构发现疑似异常 → 配置自定义监控规则 → subscribeAlert()
   链上事件触发实时推送至监管门户
   监管人员调查确认 → 在链上发布监管指令 → 交易所限期执行 → 执行结果链上核验

[执法文书上链]
   问询函/整改通知/处罚决定 → PDF 生成 SM3 哈希 → issueRegulatoryOrder()
   链上永久存证，不可篡改，可作为司法证据
```

### 场景七：资产发行、上市、退市全流程链上合规存证

```
[发行申请]

   ├─ 景区经营许可证哈希
   ├─ 门票合规性说明哈希

[重大事项公告]
   景区发生影响票价的重大事项（活动取消/改期/景区整改）

   交易所系统自动推送给持仓用户
```

## 七、高性能高可用与容灾保障方案

### 7.1 链上 TPS 优化方案

#### 预编译合约加速（C++ 底层实现）

| 预编译合约 | 功能 | 性能提升 |
|----------|------|---------|
| SM2Verify | SM2 签名验证 | Solidity 实现的 20-50 倍 |
| SM3Hash | SM3 哈希计算 | Solidity 实现的 10-30 倍 |
| BatchMerkle | 批量 Merkle 树计算 | 支持 1000 条/次批量计算 |
| SM4Cipher | SM4 对称加密/解密 | 链上数据加密场景 |

#### DAG 并行执行

FISCO BCOS 的 DAG（有向无环图）并行执行引擎针对订单存证场景的适配：

```
并行执行条件：不同用户的订单存证交易之间无数据依赖关系
→ 100% 可并行执行

串行执行场景：同一用户的账户余额更新（存在依赖，串行处理）
→ 通过「先并行存证，后批量余额更新」分离读写，最大化并行度
```

**预期 TPS**（基于 4 共识节点，内网部署）：

| 业务类型 | 预期 TPS | 峰值保障 |
|---------|---------|---------|
| 单笔订单存证 | 3,000 TPS | — |
| 批量订单存证（100条/批） | 50,000+ 订单/s | 交易高峰期 |
| 撮合记录上链 | 5,000 TPS | — |
| 清算记录上链 | 2,000 TPS | — |

#### 存证网关设计（解耦链上链下性能瓶颈）

```
存证网关架构：

撮合引擎
   │
   ▼ 异步写入（无阻塞）
缓冲队列（Redis Cluster，持久化）
   │
   ▼ 批量消费（每 10ms 或 100 条）
批处理器（多实例并行）
   │ 计算 Merkle Root
   ├─ 批量打包 → 调用 batchEvidenceOrders()
   └─ 记录批次 ID 映射（链下可对账）
        │
        ▼
   链上确认监听（监听交易回执）
        │
   确认成功：标记存证完成
   确认失败：自动重试（最多 3 次），超过告警
```

|---------|---------|---------|---------|

### 9.3 异常告警规则体系

```
内置告警规则（监管机构可调阅，不可修改；交易所可配置阈值）：

规则 R001：单笔大额交易
   触发条件：单笔成交金额 > 50万元（阈值可配置）
   告警内容：成交记录哈希 + 金额范围 + 时间戳（脱敏，不含用户身份）
   推送方式：链上事件 + 实时 WebSocket 推送至监管门户

规则 R002：账户高频交易
   触发条件：同一账户 10分钟内订单数 > 200
   告警内容：账户哈希 + 交易频率统计

规则 R003：疑似对敲交易
   触发条件：两个账户互为对手方的成交笔数 > 10次/天 且价差 < 0.1%
   告警内容：相关账户哈希 + 对敲交易记录列表

规则 R004：订单异常撤销
   触发条件：撤单率 > 80%（撤销/下单比例）
   告警内容：账户哈希 + 撤单统计

规则 R005：清算对账差异
   触发条件：链上链下清算数据不一致
   告警内容：差异成交单 ID + 差异金额范围（立即推送，无延迟）
```

### 9.4 监管指令执行全流程

```
1. 监管机构发布指令
   → 登录审计门户（CA 认证）
   → 起草指令（问询/整改/处罚/暂停/冻结）
   → 指令内容 PDF → SM3 哈希
   → ComplianceAuditContract.issueRegulatoryOrder()
   → 链上存证（不可篡改，含监管机构 SM2 签名 + 发布时间戳）

2. 交易所接收并执行
   → 链上监控服务检测到新监管指令事件
   → 推送至交易所合规负责人工作台
   → 交易所在规定时限内执行（根据指令类型：1小时/24小时/7天）
   → 执行完成 → confirmRegulatoryExecution() 上链执行结果

3. 监管机构核验执行结果
   → 在审计门户查看执行结果哈希
   → 调用 batchVerifyOrders() 等接口核验执行是否到位
   → 核验通过 → 链上标记指令闭环
   → 核验不通过 → 升级处置

4. 全链路留痕（不可删除）
   从指令发布到执行核验，全程链上存证，可作为司法证据
```

## 十、数据安全、隐私保护与全规保障方案

### 10.1 数据分级保护策略

| 数据级别 | 数据类型 | 存储位置 | 上链规则 | 访问权限 |
|---------|---------|---------|---------|---------|
| S1 极敏感 | 用户身份证号、银行卡号、人脸生物特征 | 交易所加密数据库（HSM 加密密钥） | 禁止上链明文，仅 SM3 哈希摘要 | 仅监管机构依法调取 |
| S2 敏感 | 用户真实姓名、手机号、KYC 档案 | 交易所加密数据库 | 禁止上链，链上仅存 KYC 结果（LEVEL） | 用户本人 + 合规团队 |
| S3 业务 | 订单金额、持仓数量、资金余额 | 链下系统 + 链上哈希摘要 | 以哈希形式上链 | 用户本人 + 交易所 + 监管（依法） |
| S4 公开 | 公开行情、成交量汇总、资产发行信息 | 链上明文 | 可直接上链 | 全体节点 |

### 10.2 私钥与签名安全

#### 节点私钥保护

```
所有共识节点私钥（SM2）：
├─ 存储介质：硬件安全模块（HSM，国产 SJK 系列）
├─ 操作方式：私钥不出 HSM，所有签名操作在 HSM 内部完成
├─ 备份方式：密钥分片（Shamir 秘密共享），分散存储于 3 个物理保险柜
└─ 轮换策略：每 12 个月强制轮换，旧密钥签名数据保留可验证性

用户私钥保护（方案 B - 本地签名）：
├─ iOS：存储于 Secure Enclave（SEP），生物认证解锁
├─ Android：存储于 Android Keystore（TEE 或 StrongBox）
├─ Web：使用 WebAuthn + 硬件安全密钥（YubiKey 等）
└─ 备份：BIP-39 助记词（24 词）用户自行保管，离线纸质备份
```

#### 交易所运营方私钥管理

```
密钥层级：
├─ 根密钥（Root Key）：HSM 冷存储，仅用于签署中间密钥证书
├─ 中间密钥（Signing Key）：HSM 热存储，用于日常签名操作
└─ 操作密钥（Session Key）：每日轮换，用于高频存证签名

操作审批（双人控制）：
├─ 根密钥使用：需 CEO + CTO 双人到场 + 物理令牌
└─ 合约部署/升级：需 3/5 多签

密钥泄露应急：
1. 立即通知监管机构 → 链上发布密钥撤销公告
2. 新密钥重新注册（IdentityContract.updatePublicKey，多签确权）
3. 历史签名数据可信性通过时间戳 + 监管节点存档佐证
```

### 10.3 隐私保护技术方案

#### 脱敏哈希方案

```
用户标识上链规则：
原始标识（手机号/证件号）→ 加盐 SM3 哈希 → 链上存储
盐值：用户注册时交易所生成（存储于 HSM，不上链）
效果：链上无法逆向推算原始身份，但同一用户的哈希保持一致（可关联）

防关联分析（可选增强）：
可采用零知识证明（ZKP）实现合规核验，链上仅保留核验结果，不保留任何身份关联信息
```

#### 监管数据调取流程

```
监管机构需查看用户原始身份信息时：
1. 监管机构在链上提交身份调取指令（含法律依据哈希，SM2 签名确权）
2. 交易所合规系统收到链上指令 → 触发内部审批流程
3. 交易所合规负责人确认 → 从加密数据库读取原始数据
4. 通过监管专属加密通道（SM4 加密）传输至监管机构
5. 传输记录上链存证（时间、内容摘要、双方签名）
```

### 10.4 AML/KYC 合规存证

```
KYC 数据链上存证（合规核查可用，原文不上链）：
├─ 注册时：SM3(KYC核验时间 + KYC等级 + 核验机构编码) 上链
├─ 风险等级变更：SM3(新等级 + 变更原因 + 时间) 上链
└─ AML 命中记录：SM3(命中规则类型 + 处置结论 + 时间) 上链

实名制要求（国内合规）：
└─ 所有用户开户前完成实名认证，链上身份与实名信息哈希绑定
   满足《证券法》《反洗钱法》《网络安全法》等合规要求
```

### 10.5 智能合约安全保障

#### 合约安全审计要求

```
上线前强制要求：
1. 第一轮审计：国内权威机构（如慢雾科技、知道创宇、绿盟科技）
2. 第二轮审计：交叉验证（不同机构）
3. 审计范围：合约逻辑漏洞、访问控制越权、整数溢出/下溢、重入攻击、时间戳依赖
4. 审计报告：全文上链存证，向监管机构公开

运行期持续保障：
├─ 合约不可删除原则：已上链合约不可物理删除，可通过代理模式升级
├─ 灰度升级：新版本先在测试群组运行 72 小时，无问题后切换主群组
├─ 紧急暂停：所有核心合约集成 Pausable 机制（多签触发），紧急情况暂停合约
└─ Bug Bounty：对外发布安全漏洞悬赏计划，鼓励白帽发现问题
```

#### 合约升级策略（透明代理模式）

```
代理合约（ProxyContract，永远不升级）
        │
        │ delegatecall
        ▼
实现合约（ImplementationContract，可通过多签升级）
        │
        │ 状态数据
        ▼
存储合约（StorageContract，永远不升级）

升级流程：
1. 新版本实现合约部署 → 第三方审计通过
2. 交易所 + 监管机构 3/5 多签确认升级
3. 调用 ProxyContract.upgradeTo(newImplementation)
4. 链上记录升级事件（含旧版本地址 + 新版本地址 + 升级时间 + 签名者列表）
5. 监管机构可随时查看合约版本历史
```

### 10.6 应急响应与灾难恢复

```
应急响应级别：

P0 级（立即响应，< 15 分钟）：
├─ 触发条件：撮合引擎全停 / 核心链上数据不一致 / 资金安全事件
├─ 响应动作：启动紧急预案 → 暂停交易 → 通知监管 → 容灾切换
└─ 链上操作：调用紧急暂停合约（多签）→ 链上记录紧急事件原因

P1 级（30 分钟内响应）：
├─ 触发条件：单节点故障 / 存证延迟超 30s / 监管告警误触发
└─ 响应动作：自动故障转移 + 人工确认

容灾演练要求：
├─ 频率：每季度一次全链路容灾演练
├─ 场景：节点故障切换 / 跨机房容灾 / 链上数据恢复
└─ 结果：演练报告上链存证，向监管机构公开
```
